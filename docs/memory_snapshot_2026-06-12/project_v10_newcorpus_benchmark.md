First honest v10 benchmark on the **May-26 corpus** (`SAMPLE FILES 26.05.2026`, 14 projects, ≤20MB, run 2026-06-03 after the timeout fixes): **median product recall 7%, max 25%, zero projects ≥50%.** Far below v10's 78% on the April set — because this whole corpus postdates v10's April training (all effectively holdout retail brands).

**Key diagnostic:** `tagged% == recall` in every row → recall is gated by **tag matching, not detection** (the model finds roughly the right detection *count*). And `sched_tags` (tags the schedule parser extracts) drives it: sched_tags=0 → recall≈0 (AutoZone, Crunch, Five Below, Les Schwab). So the #1 blocker is **`schedule_parser.py` returning 0 tags on retail plans** — a parser fix, NOT a retrain. Confirms the prediction in [[project-ocr-finetune-scaffold]].

**Why:** Don't waste effort on retraining/detection or more GRD work — the data says the schedule→tag pipeline is starving. **How to apply:** Next high-value task is fixing schedule extraction on the new retail corpus (start with the sched_tags=0 projects).

Timeout fix status: Tesla flipped timeout→ok (210s) after harness passes `--time-budget 450` (commit 5094fc9); but Tesla finished well under budget, so prior 600s death was partly marathon-run system load, not purely CLI. Nike = `no_detections` (separate model/page issue). Outliers: CURO truth counts every grille (534 vs ours 16, granularity mismatch); Clearwater 85% precision/7% recall (under-detects). Results in repo: `benchmark_v10_small_0603/`.

**UPDATE 2026-06-04 (commit 66f56cb):** Root cause of sched_tags=0 nailed — retail/CAD plans draw schedule tables as **vector line-art (text converted to curves), no text layer** → pdfplumber reads nothing (AutoZone schedule page: 33k curves, 68 words, all mirrored title-block junk). Built a **schedule-OCR fallback** in `schedule_parser.extract_marks_via_ocr` (fires only when text path yields <3 tags; renders pages + EasyOCR + strict tag filter) plus a `takeoff_cli` product-refinement (generic AD-GRD detection + matched tag → specific class, e.g. CD→AD-T-BAR SUPPLY, RG→RETURN; scoped to OCR-fallback projects only). **AutoZone product recall 4%→54%.** Verified text-layer Dick's unchanged (fallback doesn't fire, 57 tags). Known gaps / next work: (1) ~50 diffusers still untagged = bubble-OCR misses (the real headroom to ~75%); (2) returns (RG) + toilet exhaust fans (TEF-n) under-read by OCR; (3) mounting defaults to T-BAR (wrong for surface-mount projects); (4) schedule-OCR is slow (~200-240s/plan, full-page EasyOCR); (5) full-corpus benchmark of the fallback still pending. Important: many retail tags are BARE (AutoZone tags all 62 supply diffusers "CD", all 16 returns "RG" — differentiated only by neck size).

**UPDATE 2026-06-04b:** (a) Scored v10 on holdout text-based plans (`SAMPLE FILES 02.06.2026`): **median product recall ~33%, precision ~80%, max 100%** — much higher than the 7% mixed-corpus median, confirming vector schedules (not the model) are the bottleneck. Doc: `docs/text_based_accuracy_2026-06-04.md`. (b) **Fixed per-stage budgeting** (commit ed9336b): detection used to eat the whole `--time-budget`, starving tag inference (skipped → 0-tagged large plans). Now an adaptive tagging reserve sized to detections-found (~1s each, cap 50%), recomputed per page; detection-light plans reserve ~nothing (no recall regression). Validated HM SSC: 42 dets + tagging runs (vs fixed-30% over-cut to 33). TWO large-plan bottlenecks REMAIN, separate from this: (1) schedule parse still eats ~40% of budget (pdfplumber extract_tables/page on 45–103pp) → **streaming pdfplumber is the real fix**; (2) **AD-GRD→AD-T-BAR class-bridging** — Level-1 direct-mapping doesn't bridge generic detection class to specific schedule class, so tagged-count stays low even when tagging runs (doesn't hurt class-based product recall, but blocks tag-level detail).
